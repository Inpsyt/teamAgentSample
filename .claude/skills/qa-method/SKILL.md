# QA 방법론 (qa-method)

ISTQB 표준의 블랙박스 테스트 설계 기법으로 화면 정의서에서 테스트 케이스를 도출한다.

## 1. 테스트 케이스 설계 기법 (체크리스트 추출 시 적용)

| 기법 | 적용 대상 | 방법 |
|---|---|---|
| **동등 분할** | 입력 필드·선택지 | 같은 결과를 내는 입력을 그룹으로 묶고 그룹당 대표값 1개만 테스트 (유효 그룹 + 무효 그룹 각각) |
| **경계값 분석** | 범위·길이 제한 | 경계 직전/경계/직후 값 테스트 (예: 최대 20자 → 19·20·21자). 버그는 경계에 몰린다 |
| **결정 테이블** | 조건 조합 (권한×상태 등) | 조건 조합별 기대 결과를 표로 만들고 각 열을 1케이스로 |
| **상태 전이** | 단계형 플로우 (주문·가입) | 정의서의 상태 다이어그램에서 유효 전이 + **무효 전이 시도**(뒤로가기, URL 직접 진입)를 케이스로 |

- 정의서의 예외 케이스 4종(빈 상태/오류/로딩/권한 없음)은 위 기법과 별개로 전 화면 공통 케이스다
- 모든 케이스는 관련 SCR/REQ ID를 갖는다 — ID 없는 케이스를 만들었다면 정의서 공백이므로 리포트에 "정의서 보완 필요"로 기록

## 2. 탐색적 테스트 (체크리스트 이후 보완)

체크리스트 실행 후 시간이 허용하면 차터 기반 탐색 세션을 1회 수행한다:

- 차터 형식: "〈화면·기능〉을 〈관점〉으로 탐색한다" (예: "검색 결과를 특수문자·긴 문자열 입력 관점으로 탐색")
- 발견 결함은 체크리스트 결함과 동일 형식으로 기록하되 `탐색적` 태그를 단다

## 3. 결함 리포트 표준

결함 1건당 필수 항목:

- **재현 절차**: 번호 매긴 단계 — 다른 사람이 그대로 따라 하면 재현되어야 함
- **기대 결과 vs 실제 결과**: 기대는 정의서 근거(SCR/REQ 인용), 실제는 관찰 사실만
- **증거**: 스크린샷 (콘솔 오류가 있으면 함께)
- **심각도와 우선순위 구분**:
  - 심각도(상/중/하) = 시스템 영향 (데이터 손실·차단 / 주요 기능 오동작·우회 가능 / 표시 결함)
  - 우선순위는 QA가 정하지 않는다 — 심각도만 판정하고 수정 순서는 PM·사용자 판단에 맡긴다
- 재현 불가 결함은 버리지 않고 "간헐적 — 재현 조건 미상"으로 기록

## 흔한 실수

- 유효 입력만 테스트 (무효 동등 그룹 생략) — 케이스 수의 절반은 무효 입력이어야 정상
- 경계값 대신 임의 중간값만 테스트
- "잘 안 됨" 식 결함 기록 — 재현 절차와 정의서 근거가 없으면 결함이 아니라 소감
- 심각도에 수정 시급성을 섞음 (오탈자라도 메인 화면이면 시급할 수 있으나, 심각도는 여전히 "하")
