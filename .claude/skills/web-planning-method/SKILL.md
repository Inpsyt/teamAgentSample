# 웹기획 방법론 (web-planning-method)

## 1. Garrett UX 5단계 층위 — 산출물의 위치 확인

Jesse James Garrett 『The Elements of User Experience』의 5개 층위. 각 산출물이 어느 층위인지, **바로 아래 층위의 근거가 있는지** 먼저 확인한다.

| 층위 | 내용 | 이 팀의 산출물 |
|---|---|---|
| ⑤ 표면 | 시각 디자인 | (디자인 조직 담당) |
| ④ 골격 | 화면 레이아웃·인터페이스 | 화면 정의서 |
| ③ 구조 | IA·인터랙션 흐름 | IA 문서, 유저 플로우 |
| ② 범위 | 기능 요구사항 | 요구사항 정의서 |
| ① 전략 | 사용자 니즈·사업 목표 | 기획서·리서치 (10-research, 20-drafts) |

- 화면 정의서(④)를 쓰는데 요구사항(②)이 없으면: 작성은 하되 "선행 요구사항 정의 권장"을 최종 응답에 명시한다
- 하위 층위 문서와 상충하는 내용을 상위 층위에 쓰지 않는다

## 2. IA 4대 구성 체계 (Rosenfeld & Morville)

IA 문서는 4가지 체계를 각각 답해야 완성이다:

- **조직화**: 콘텐츠를 어떤 기준으로 묶는가 (주제별/작업별/사용자 유형별) — 기준을 문서에 명시
- **레이블링**: 메뉴·버튼 명칭 — 사용자 언어로, 동일 대상은 전 화면에서 동일 명칭
- **내비게이션**: 전역/지역/맥락 내비게이션 구분, 현재 위치 표시 방법
- **검색**: 검색 대상 범위·결과 형태 (검색이 없다면 "제공 안 함"과 사유)

## 3. 요구사항 품질 기준 (ISO/IEC/IEEE 29148)

각 REQ 항목은 아래를 만족해야 한다. 검토 시 체크리스트로 쓴다:

- **단일성**: 한 항목 = 한 요구사항 ("~하고 ~한다"는 분리)
- **명확성**: 두 가지로 해석 불가. "빠르게", "적절히" 같은 수식어 금지 — 수치나 조건으로
- **검증 가능성**: 통과/실패를 판정할 방법이 존재 (QA가 테스트 케이스로 바꿀 수 있는가)
- **추적 가능성**: 상위 근거(기획서·리서치)와 관련 화면(SCR)을 상호 참조
- **실현 가능성 표기**: 기술 검토가 필요한 항목은 `[기술 검토 필요]` 표시

## 4. 인수 기준 — Given-When-Then

핵심 인터랙션·예외 케이스는 Given-When-Then 형식으로 쓴다:

```
Given: 로그인하지 않은 사용자가 상품 상세에 있을 때
When: 구매하기를 누르면
Then: 로그인 화면으로 이동하고, 로그인 후 원래 상품 상세로 복귀한다
```

- 예외 케이스 4종(빈 상태/오류/로딩/권한 없음)은 각각 최소 1개의 Then을 가진다
- 유저 플로우 다이어그램은 해피 패스 1개 + 주요 예외 분기를 포함한다 (해피 패스만 있는 플로우는 미완성)

## 흔한 실수

- "관리자는 회원을 관리할 수 있다" 류의 검증 불가 요구사항 (무엇이 되면 통과인가?)
- 화면마다 같은 기능의 레이블이 다름 (장바구니/카트/담은 상품)
- 예외 케이스 섹션을 "일반 오류 처리"로 뭉뚱그림 — 4종 각각 구체 화면 동작으로
- IA에 조직화 기준 설명 없이 트리만 그림 → 리뷰·확장 시 판단 근거가 없음
